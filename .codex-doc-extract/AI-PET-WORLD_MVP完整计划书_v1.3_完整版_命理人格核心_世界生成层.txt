0. v1.3 版本修正说明
本版本用于修正 v1.2 中“管家与宠物同时作为 MVP 默认主线”的业务表达。v1.3 不推翻命理人格核心、世界生成层、Renderer 数据驱动原则和像素资产管线，而是重新定义 AI-PET-WORLD 的业务主线：先生成管家，再让世界围绕管家的自主意识、人格倾向、资源判断、建设行为和生命关系选择逐步展开。
v1.3 的核心变化不是“删除宠物”，也不是“改成另一个项目”。宠物仍然是 AI-PET-WORLD 的重要生命类型，但宠物不再是每个玩家开局必然拥有的默认对象。宠物从“开局资产”调整为“生命关系事件”：在世界运行过程中，由管家人格、当前资源、世界安全感、居住条件、记忆状态与关系倾向共同决定是否观察、靠近、准备、延迟、拒绝或接纳。
因此，MVP 的优先验证对象从“管家照顾宠物”调整为“玩家生命信息生成的管家，能否在一片初始世界中独立生活、自主判断、自主建设，并形成可被玩家观察到的差异化世界轨迹”。
1. 产品一句话定义
AI-PET-WORLD 是一个以玩家真实生命信息为源头，由命理人格算法生成 AI 管家底层人格，再由管家自主意识、世界规则、资源循环和长期记忆共同驱动家园成长的 AI 生命世界。
玩家不是直接操作者，而是世界源头、观察者和陪伴者。管家不是工具人，而是玩家生命信息映射出的第一生命。宠物不是普通宠物素材，也不是开局默认资产，而是世界运行后可能被管家接触、判断、接纳并建立关系的独立生命。
v1.3 的产品重心是：先让“管家是谁”成立，再让“管家如何生活”成立，最后再让“管家是否愿意与另一个生命建立关系”成立。
2. MVP 总目标
AI-PET-WORLD MVP 不是一次性完成完整游戏，也不是做一个好看的静态像素页面。v1.3 MVP 必须证明以下核心闭环成立：
1. 玩家输入真实生命信息后，系统能生成管家的源头人格、管理风格、生活倾向和建设倾向。
2. 管家作为第一生命进入世界，世界初始状态可以没有宠物，但必须可以独立运行。
3. 世界能生成一个可见、可保存、可继续变化的初始像素家园。
4. 管家能根据资源、天气、时间、空间结构、记忆、事件和人格倾向，自主形成生活意图与建设意图。
5. 管家的行为结果不是直接改前端页面，而是生成 ConstructionPlan / MapDiff / placements / eventLogs 等结构化世界变化数据。
6. 宠物作为后续生命关系事件出现，管家可以观察、靠近、准备、延迟、拒绝或接纳。只有当接纳发生后，宠物系统才进入主运行闭环。
7. 前端 Renderer 只负责稳定渲染 HomeMapState 和 WorldState，不负责创造世界、不负责决定宠物是否出现、不负责绕过规则摆放素材。
MVP 的最小成功标准不是“地图好看”，而是：玩家打开 /world 后能看到一个真实可理解的像素家园，并且这个家园能够在没有宠物的情况下继续运行；不同玩家生成的管家，会因为人格不同而出现不同的生活节奏、建设优先级、解释语气、关系选择和世界变化。
3. 完整核心架构：横向八层 + 纵向生命线层
AI-PET-WORLD v1.3 继续采用“横向八层 + 纵向生命线层”的架构，但业务主线调整为管家先行。宠物相关系统保留接口与扩展位置，但不再作为开局强依赖。
横向八层
1. 玩家源头层：玩家真实出生信息、世界 seed、账户世界入口。
2. 命理人格层：紫微斗数 / 八字输入规范化、排盘、星曜、宫位、组合与人格映射。
3. 人格映射层：BirthPattern -> PersonalityProfile -> 管家行为倾向、建设风格、关系倾向、视觉倾向。
4. 意识核心层：管家的自主意识、当前关注、判断、犹豫、靠近、回避、计划与解释。宠物出现后再接入宠物意识。
5. 状态 / 记忆 / 关系层：管家短期状态、长期记忆、世界事件历史；宠物关系在生命事件被接纳后再建立。
6. 自主驱动层：rest、explore、observe、approach、avoid、maintain、build 等驱动决定行为优先级；eat 等生理驱动按生命类型接入。
7. 行为执行层：管家任务、建设阶段、路径移动、世界交互、关系选择；宠物动作在宠物出现后进入。
8. 世界运行层：worldEngine、时间、资源、生态、地图、离线运行、持久化。
纵向生命线层
纵向生命线层贯穿所有层。它负责长期阶段、成长轨迹、AI 世界时间、未来 AI 纪元、管家生命阶段、家园成长阶段、生命关系阶段和后续社区化扩展。MVP 阶段只实现管家个人世界与家园成长，不把多人社区作为当前主线。
4. 业务主线：管家先行，宠物后置
v1.3 的核心业务逻辑为：玩家不是直接养宠物的人，而是一个世界的生命源头。玩家输入真实生命信息后，系统生成一个映射玩家生命信息的 AI 管家。管家作为第一生命进入世界，先面对空地、资源、天气、时间和基础生活需求。宠物不是系统强制送给玩家的开局对象，而是在后续世界运行中出现的生命关系事件。
4.1 开局业务流程
1. 玩家创建世界并输入真实生命信息。
2. personality-core 根据真实时间生成 ButlerPersonalityProfile。
3. 系统根据玩家信息、管家人格和 worldSalt 生成稳定 worldSeed。
4. InitialHomeGenerator 生成初始 HomeMapState：空地、临时住所、基础资源、路径雏形、自然边界、管家站位。
5. Renderer 读取 HomeMapState 渲染世界。
6. worldEngine 启动，优先更新时间、资源、管家状态、管家意图、建设事件和日志。
7. 宠物系统处于未激活状态，直到生命关系事件被触发并被管家接纳。
4.2 管家独立生活阶段
管家独立生活阶段是 v1.3 MVP 的核心阶段。这个阶段需要证明：即使没有宠物，世界也不是空转；管家会根据人格与环境做出不同生活选择。
• 建设型管家会优先整理路径、搭建临时住所、规划地基和储物区。
• 照护型管家会更早考虑生命接纳条件，例如水源、食物角、安静空间和安全边界。
• 防御型管家会优先围栏、边界、观察点、避难角落和路径安全。
• 审美型管家会优先花草、灯、庭院布局、视觉秩序和氛围。
• 安静维护型管家会低频建设，更注重稳定、修补、清理和耐久。
• 探索型管家会更频繁调查资源点、边界、痕迹和未知区域。
4.3 生命关系事件阶段
生命关系事件不是开局默认发生，也不是单纯随机刷新。它由世界运行状态触发，再由管家人格与当前条件判断。事件可以表现为远处出现动物痕迹、草丛有动静、路边出现受伤小动物、门口留下足迹、夜间听到微弱声音、资源区出现陌生生命等。
管家的可能决策包括：observe_life（观察）、approach_life（靠近）、prepare_for_life（准备）、delay_life_contact（延迟）、reject_life_contact（拒绝）、accept_companion（接纳）。只有 accept_companion 发生后，宠物才正式进入玩家家园世界。
5. 命理人格核心层（紫微斗数 / 八字）
命理人格核心是 AI-PET-WORLD 的第一护城河，v1.3 不重写该层。没有命理人格核心，AI-PET-WORLD 会退化成普通像素经营或普通宠物游戏；有这一层，管家人格、建设风格、关系选择和世界成长才有“个体差异”和“生命源头”。
核心原则
1. 玩家真实出生信息用于生成管家的源头人格、管理风格、生活倾向和关系倾向。
2. 宠物人格不由孵化仓、胚胎或 hatch 概念产生；宠物只有在生命关系事件被接纳并发生真实抵达 / 分配时，才生成宠物人格底色。
3. 游戏世界时间可以加速，但真实命理时间不能被游戏时间加速。
4. 正式 UI 不显示紫微斗数术语，只显示人格结果、行为倾向、管家解释和世界变化。
5. 调试页可以显示时辰、星曜、宫位、BirthPattern、PersonalityProfile 等内部信息。
6. personality-core 是稳定核心，不因世界生成层、Renderer 或宠物后置主线而重写。
MVP 必须保留的命理核心文件职责
• src/ai/personality-core/lunar.ts：公历转农历、时辰映射、真实时间输入规范化。
• src/ai/personality-core/ziwei-engine.ts：紫微斗数核心排盘计算，包括命宫、身宫、十二宫、紫微/天府、十四主星、对宫、三方四正等核心结构。
• src/ai/personality-core/calculator.ts：适配层，只负责把 ziwei-engine 输出转为 BirthPattern，不再承担核心排盘逻辑。
• src/ai/personality-core/mapper.ts：BirthPattern -> PersonalityProfile，映射性格、标签、摘要、权重、行为倾向、建设倾向与关系倾向。
• src/ai/personality-core/constants.ts：权重、阈值、空宫/借宫强度等常量。
• src/ai/personality-core/evolution.ts：未来成长、时间漂移、长期阶段影响的占位层。
• src/ai/personality-core/gateway.ts：统一入口，只暴露 buildBirthPattern、buildPersonalityFromPattern、buildPersonalityProfile。
• src/ai/personality-core/schema.ts：BirthPattern、PersonalityProfile、trait、tag、summary 等类型定义。
知识库目录必须保留
• knowledge/starProfiles.ts：十四主星单星人格基线。
• knowledge/pairRelations.ts：星曜组合关系。
• knowledge/pairProfiles.ts 与 pairProfiles/*：组合人格配置。
• knowledge/labels.ts：动态标签生成。
• knowledge/priorities.ts：组合启用与优先级。
• knowledge/summaries.ts：人格摘要、去重、聚合。
• knowledge/emptyState.ts：空宫、借对宫、虚化倾向。
MVP 阶段不要求完整大运、流年、流月、流日，但必须保留扩展口。ziwei-engine.ts 当前应视为稳定核心，除非明确扩展星曜/时间层，否则不随 UI、地图或业务主线阶段重写。
6. 命理人格算法管线与输出结构
命理人格核心的 MVP 管线如下：
1. BirthInput：year、month、day、hour、minute、timezone、gender / perspective 等。
2. Time Normalization：将 24 小时制真实时间转换为十二时辰。正式 UI 仍显示 24 小时制，不显示命理术语。
3. Lunar Conversion：公历 -> 农历，并获得命理计算所需年月日时。
4. Ziwei Plate：ziwei-engine 计算命盘结构。
5. BirthPattern：calculator 把底层命盘转换为产品可用人格模式。
6. PersonalityProfile：mapper 输出人格倾向、行为偏好、建设风格、情绪敏感度、秩序/探索/照护/守护/关系接纳等权重。
7. Runtime Influence：世界状态、记忆、资源、事件对人格结果进行短期调制，但不覆盖底层人格。
结构化输出要求
• corePersonality：核心人格描述。
• traits：行为、情绪、驱动、建设、关系倾向。
• tags：人格标签，用于事件叙事、建设风格、视觉风格和管家解释。
• constructionStyle：管家建设风格权重。
• lifeRhythmBias：管家独立生活节奏，例如整理、观察、建设、休息、探索、维护。
• companionDecisionBias：管家面对生命关系事件时的接纳、观察、延迟、拒绝倾向。
• relationBias：关系建立方式，例如慢热、守护、亲近、独立、谨慎、依赖。
• eventTone：事件表达风格。
• debugLogs：调试页可见，正式 UI 不显示。
十四主星必须作为人格底层基线，不再使用抽象 core_symbol。组合人格使用 pairRelations + pairProfiles。空宫不是错误，而是通过借对宫、三方四正修正、虚化倾向形成独特人格表现。
7. 管家人格生成与独立生活逻辑
管家是玩家生命信息映射出的自主意识管理者，不是普通 NPC，也不是宠物系统的附属照护工具。v1.3 MVP 必须把“玩家源头 -> 管家人格 -> 管家独立生活 -> 管家建设世界 -> 管家选择关系”接入主线。
管家生成流程
1. 玩家输入真实出生年月日 / 出生时间。
2. personality-core 生成 ButlerPersonalityProfile。
3. PersonalityProfile 映射为 ButlerConstructionStyle、LifeRhythmBias、CompanionDecisionBias。
4. 管家进入初始世界，以该人格风格进行观察、整理、建设、维护、记录和解释。
管家生活与建设风格字段
• structured_builder：优先路径、地基、储物、秩序结构。
• warm_caretaker：优先舒适、温暖、照护准备、水源、食物角、安静空间。
• protective_keeper：优先围栏、安全角落、观察点、边界、避险路线。
• aesthetic_organizer：优先花草、灯、装饰、庭院美感、视觉协调。
• quiet_maintainer：优先稳定、低调、耐久、安静区域、低频维护。
• adaptive_planner：根据资源、天气、事件、记忆和关系变化动态调整。
• exploratory_surveyor：优先调查未知区域、资源点、边界痕迹和环境变化。
管家独立行为池
• observe_world：观察天气、地形、资源、边界、痕迹。
• clean_area：整理草地、清理落叶、移动石块、清出道路雏形。
• build_shelter：搭建或加固临时住所。
• mark_boundary：标记边界、设置观察点、形成安全范围。
• collect_resource：收集木材、石头、泥土、水、可用材料。
• plan_layout：规划路径、住所、储物、安静区、未来生命接触区。
• rest_and_record：休息、记录、回顾事件、形成管家解释。
• respond_to_life_trace：对生命痕迹进行观察、靠近、延迟或准备。
MVP 验收：同样的世界资源条件下，不同玩家生成的管家，在生活节奏、建设优先级、解释语气、区域选择、视觉倾向和生命关系选择上应出现可观察差异。
8. 宠物作为生命关系事件
宠物是独立自主生命，不是玩家手里的道具，也不是系统开局强制发放的资产。v1.3 中，宠物系统不删除，但从“开局主线”调整为“生命关系事件被接纳后的运行系统”。
宠物出现原则
1. 开局世界可以没有宠物，worldEngine 必须能在 pet 缺失的情况下正常运行。
2. 宠物不通过孵化仓 / 胚胎 / hatch 进入产品层。
3. 宠物不再默认通过固定领养流程强制进入家园，而是通过生命关系事件、世界事件、系统分配或后续扩展入口进入。
4. 管家是否接纳宠物，由管家人格、资源条件、住所稳定度、安全感、记忆、近期事件和关系倾向共同决定。
5. 宠物被接纳后，才根据真实抵达 / 分配时刻生成 PetPersonalityProfile。
6. 宠物人格影响行为倾向，但宠物行为仍由人格 + 当前状态 + 记忆 + 环境共同决定。
7. 宠物不能在事件文本里说人话。事件表达应以动作、状态、情绪、环境反应为主。
管家面对生命事件的决策结果
• ignore_life_trace：注意到痕迹但不介入。
• observe_life：保持距离观察。
• approach_life：缓慢靠近，确认状态。
• prepare_for_life：提前准备水源、休息角、安全区域。
• delay_life_contact：当前条件不足，延迟接触。
• reject_life_contact：明确不接纳，世界继续独立运行。
• accept_companion：接纳该生命，创建宠物抵达事件并激活宠物系统。
宠物人格输出应用
• 行为偏好：探索、观察、接近、回避、休息、进食等概率偏移。
• 情绪敏感度：对天气、管家靠近、陌生区域、资源变化的反应。
• 关系建立：慢热、亲近、守护、独立、依赖等倾向。
• 视觉表现：体型、颜色、眼神、耳尾、动作幅度等后续视觉映射。
MVP 先做到：宠物系统可以后置激活；宠物一旦出现，拥有可被行为系统读取的人格 profile；正式 UI 不暴露紫微术语。
9. 世界时间、资源与建设规则
AI-PET-WORLD 的时间分为三层，必须写入 MVP 规则并进入代码设计。
1. 真实命理时间：用于玩家管家人格、宠物抵达人格，不加速。
2. AI 世界时间：用于昼夜、资源、天气、管家生活、管家建设、宠物作息，可加速。
3. AI 纪元时间：未来用于世界历史、长期阶段、社区文明和跨世界演化，MVP 只保留概念。
正式 UI 使用 00:00-23:59 的 24 小时制。后台可以转换十二时辰，但正式世界页不显示子、丑、寅等术语。调试页可以显示内部映射。
资源规则
• 资源不是商城凭空刷新。
• 资源有位置、恢复速度、消耗方式和生态关系。
• 建设不能凭空发生，必须有土地、空间、材料、时间和管家意图。
• 草地、树、落叶、石头、木材、泥土、水、休息空间都是世界资源的一部分。
• 宠物尚未出现时，资源消耗主要来自管家生活、建设、维护和探索。
• 宠物出现后，资源系统再额外接入食物、水、休息区、照护消耗和关系事件。
建设规则
玩家不直接点击建造。家园变化来自管家判断、资源状态、天气、时间、事件和人格倾向。宠物需求不再是 MVP 初始建设的唯一驱动力，而是在宠物被接纳后成为建设评分的一部分。
10. 世界生成与自主建设层
这是 v1.3 继续保留的核心功能层，用于解决“AI 直接写前端 UI 很丑、布局不自然、素材随机摆放”的根本问题。该层不是 UI，也不是单纯 worldEngine，而是把人格、资源、需求、建设意图转换成可见地图变化的中间层。
核心模块
1. World Seed System：根据玩家 ID、真实出生信息、worldSalt 生成稳定世界种子。
2. HomeMapState：保存玩家当前家园地图，包括 zones、placements、resources、constructionPlans、mapDiffs、lifeEvents。
3. Initial Home Generator：根据 seed、管家建设风格、P0 素材包和 scene recipe 生成第一张初始家园。
4. Placement Engine：按规则摆放素材，负责地面承托、路径连续、碰撞检测、装饰密度、区域关系。
5. MapDiff / Persistence：每次建设以增量变化写入地图，不覆盖整个世界。
6. Construction Planner：管家根据资源状态、天气、事件、记忆和人格形成建设意图。宠物出现后再把宠物需求纳入评分。
7. Construction Executor：将建设计划分阶段执行，玩家能看到家园逐步变化。
8. Life Event System：根据世界条件触发生命痕迹、陌生生命靠近、受伤小动物等事件。
9. Companion Decision System：根据管家人格和世界状态判断观察、靠近、准备、延迟、拒绝或接纳。
10. Renderer：前端只读取 HomeMapState / placements / MapDiff / WorldState 渲染，不自由设计地图。
正确顺序
首次进入：玩家真实信息 -> 管家人格 -> worldSeed -> InitialHomeGenerator -> HomeMapState -> Renderer -> 玩家看到初始家园。
日常运行：worldEngine tick -> 管家感知资源、天气、事件、记忆 -> ConstructionPlan 或 LifeEventDecision -> Rule / Constraint Check -> PlacementEngine -> MapDiff -> Renderer -> 玩家看到家园成长。
宠物进入：LifeEvent 触发 -> 管家决策 accept_companion -> 记录真实抵达 / 分配时刻 -> personality-core 生成 PetPersonalityProfile -> petSystem 激活 -> Renderer 显示宠物与关系状态。
11. 像素世界设计系统与 Initial Home Scene Recipe
AI-PET-WORLD 的前端不能再让 AI 自由设计。正式 /world UI 必须遵循像素世界设计系统。v1.3 的初始家园不再默认围绕宠物设施展开，而是围绕“管家第一生命进入空地”展开。
核心原则
1. 原型图只代表业务关系，不代表最终视觉。
2. 参考图只学习画面组织方式，不照抄内容。
3. /world 正式页面不能默认显示白色网格和坐标标签。
4. 地图不是在草地上贴图标，而是区域、地面、道路、承托、主体、装饰、角色、氛围组成的世界。
5. 任何建筑或设施不能孤立摆放。
6. 帐篷、临时住所或工具点必须有泥地 / 木板 / 阴影承托。
7. 储物箱、工具、火堆、水桶等基础设施必须与生活区、路径或资源点建立关系。
8. 宠物相关设施不作为开局必备项，只在管家准备生命接纳或宠物被接纳后出现。
9. 生命接触点必须是自然空地、草丛边缘、路径旁或资源区附近，不是科幻传送门，也不是孵化仓。
初始家园区域模板
• 管家抵达区：自然空地、草泥边缘、小石头、脚印、连接住所区的路径。
• 临时住所区：帐篷或简易棚、泥地 / 木板底座、小灯、储物、路径连接。
• 资源整理区：木材、石头、落叶、可收集材料、水桶或工具箱。
• 观察边界区：树、灌木、石头、小花、落叶形成外围边界与安全感。
• 安静休息区：草边阴影、小灯、木凳、低干扰区域。
• 生命接触预留区：不是默认宠物区，而是未来生命事件可能发生的位置，例如草丛边、路口、树下空地。
12. Pixel Asset Pipeline：MVP 像素资产生产管线
MVP 阶段不适合让像素师全量制作正式美术。正确策略是低保真温暖自然像素拼图风 + P0 最小资产包 + AI 生成候选 + 人工筛选修正 + 后续正式替换。v1.3 的 P0 资产优先服务管家独立生活和初始家园，不强制包含完整宠物照护套件。
MVP 风格定位
• 32x32 tile 为基础。
• 低饱和度自然色。
• 俯视 / 轻微 3/4 视角。
• 温暖、柔和、自然。
• 不追求商业精美像素，不做复杂动画。
• 不做成熟营地，不做现代露营地，不做科幻基地。
像素师参与策略
不做全量外包。若预算允许，只做风格锚点包：草地、泥地、道路、草泥边缘、临时住所、木板底座、储物箱、工具、木材堆、小树、灌木、灯、管家 idle。这批素材用于确定颜色、比例、边缘、像素密度、视角和整体风格。
P0 最小素材包
• 地面：ground_grass_base_01、ground_grass_base_02、ground_dirt_base_01。
• 道路：path_dirt_horizontal_01、path_dirt_vertical_01、四个转角。
• 边缘：edge_grass_dirt_top/bottom/left/right。
• 自然：nature_tree_small_01、nature_bush_small_01。

每张素材必须通过透明背景、尺寸正确、风格统一、无黑底、无残影、无脏点、可注册 assetId、可被 Placement Engine 调用的验收。

15. 核心数据结构草案
HomeMapState
保存玩家当前家园世界。字段：worldId、ownerId、seed、mapSize、zones、placements、resources、constructionPlans、mapDiffs、lifeEvents、createdAt、updatedAt。
WorldRuntimeState
保存世界运行状态。字段：worldTime、weather、season、butlerState、petState?、activeLifeEvents、recentEvents、resourceSnapshot、phase。petState 必须是可选字段。
ButlerState
字段：id、profileId、currentAction、focusTarget、energy、mood、memoryRefs、activeIntent、lifeRhythmBias、companionDecisionBias。
LifeEventState
字段：eventId、type、triggerReason、location、visibility、urgency、safetyLevel、requiredResponse、status、createdAt。
CompanionDecision
字段：decisionId、lifeEventId、decisionType、confidence、personalityBias、resourceCheck、safetyCheck、memoryInfluence、reason、nextReviewTime。
PetState
字段：id、profileId、arrivalTime、status、currentAction、relationshipToButler、needs、memoryRefs。该字段只在 accept_companion 后创建。
MapPlacement
字段：id、assetId、x、y、layer、scale、variant、anchor、reason、createdBy。
ConstructionIntent
字段：type、sourceNeed、urgency、personalityBias、reason、preferredZone。v1.3 中 sourceNeed 可以来自管家生活、资源维护、环境安全、生命事件准备；不要求必须来自宠物需求。
ConstructionPlan
字段：projectType、targetZoneId、requiredResources、requiredTime、stages、layoutRecipeId、placements、expectedEffects。
MapDiff
字段：diffId、worldDay、addedPlacements、removedPlacements、updatedZones、resourceTransactions、eventIds。
PersonalityProfile 必须能输出 constructionStyle、lifeRhythmBias、companionDecisionBias 与 relationBias，使命理人格层可以影响世界生成层、管家生活层和生命关系决策层。
16. MVP 数据流与运行闭环
首次进入
玩家输入真实生命信息 -> personality-core 生成 ButlerPersonalityProfile -> constructionStyle / lifeRhythmBias / companionDecisionBias -> World Seed -> Initial Home Generator -> HomeMapState -> Renderer -> 玩家看到初始家园。
管家日常运行
worldEngine tick -> 管家感知资源、天气、时间、地图、事件、记忆 -> ButlerIntent -> Construction Planner 或 LifeEvent Response -> Constraint Check -> Placement Engine / Event System -> MapDiff / EventLog 写入 -> Renderer 渲染变化 -> 管家解释。
生命事件出现
worldEngine tick -> life-event-generator 根据世界条件生成生命痕迹 -> butlerSystem 读取管家人格和当前状态 -> companion-decision 输出 observe / approach / prepare / delay / reject / accept -> eventSystem 记录过程 -> Renderer 显示痕迹、管家动作或地图准备变化。
宠物被接纳
accept_companion -> 记录真实抵达 / 分配时刻 -> personality-core 生成 PetPersonalityProfile -> petSystem 激活 -> worldEngine 将 petState 纳入循环 -> Renderer 显示宠物 -> Construction Planner 后续把宠物需求纳入建设评分。
宠物未被接纳
reject_life_contact 或 delay_life_contact -> petSystem 不激活 -> 世界继续以管家独立生活和家园建设为主线运行 -> 生命事件可在未来根据条件再次出现。
17. Codex 开发纪律
1. 不允许再让 AI 自由设计 /world 地图。
2. AI 不直接写最终 UI 布局，AI 只能输出结构化数据、计划、解释或候选方案。
3. 正式 /world 不默认显示 debug grid / 坐标标签。
4. 不恢复旧 WorldObserveLayout、WorldPixelStage、P-Phone、MiniMap、DeveloperDock。
5. 不在正式 UI 显示紫微斗数术语。

18. MVP v1.3 验收标准
• 产品方向：玩家打开世界后能明显看出这是像素生命世界，不是文字游戏，也不是静态地图。
• 命理核心：玩家真实出生信息能生成管家人格；正式 UI 不显示紫微术语。
• 管家主线：管家作为第一生命可以独立生活、观察、整理、建设、休息、解释。
• 无宠物运行：开局没有宠物时，worldEngine、WorldState、Renderer、事件日志不报错、不空转。
• 宠物后置：宠物只能通过生命关系事件和管家接纳进入主循环，不能作为开局强制资产。
• 管家规则：玩家不直接建造，管家基于资源、天气、事件、记忆和人格自主建设。
• 世界生成：同一玩家 seed 生成稳定初始家园，刷新不会随机变化。
• 地图状态：HomeMapState 可保存、读取、渲染。
• Placement：设施不孤立，路径连续，建筑有承托，草地不棋盘化。
• 像素资产：P0 素材包以管家和初始家园为核心，可用、透明背景、风格统一，能进入 registry。
• UI：/world 默认不显示白色网格，不是坐标测试图。
• 行为：管家状态、建设状态、生命事件状态能在世界中体现，后续建设能通过 MapDiff 显示。
• 技术：lint、tsc、build 全通过。

20. 最终结论
最终结论：MVP v1.3 不是把 AI-PET-WORLD 改成别的项目，而是把原本的“宠物默认开局”改为更符合人格驱动世界逻辑的“管家先行，宠物后置”。
AI-PET-WORLD 的 MVP 必须同时包含：
1. 命理人格核心：决定管家是谁。
2. 管家第一生命主线：决定世界如何从玩家生命信息开始运行。
3. 世界运行核心：决定时间、资源、天气、事件如何流动。
4. 世界生成与自主建设层：决定家园如何长出来。
5. 生命关系事件层：决定宠物是否、何时、以什么关系进入世界。
6. 像素资产管线：提供可被生成系统调用的积木。
7. Renderer：让玩家真正看见世界。
没有命理人格核心，项目会失去护城河；没有管家第一生命主线，项目会退回普通宠物照护；没有世界生成层，项目会变成静态 UI；没有生命关系事件层，宠物只会变成默认资产；没有 Renderer，玩家无法体验。
MVP v1.3 的目标是先跑通一个完整闭环：玩家输入真实生命信息 -> 生成管家人格 -> 生成初始家园 -> 管家独立生活与建设 -> 生命事件出现 -> 管家自主决定是否接纳宠物 -> 玩家看到家园与关系逐步变化。
