25. 最终结论
1. 三份文档审核结论
三份文档的主方向是正确的：人格驱动、规则生成、非固定布局、结构化状态容器、FormalVisualModel First、宠物后置、UI 只读。这些都必须保留。问题在于旧版本还没有把“世界本身的生态规律、资源有限性、自动建设与维护、社区/小镇演化”写到足够工程化，因此开发时容易把项目误解成“地图生成器”或“宠物 UI”。
1.1 本版保留的核心结论
世界事实必须来自规则、状态和结构化容器，不能来自前端组件或 PNG 素材。
同一玩家、同一 seed、同一状态下，世界必须稳定复现；不同人格、资源和事件下，世界必须有可观察差异。
管家是玩家生命信息映射出的自主管理者，不是执行玩家按钮指令的 NPC。
玩家不直接建造家园，不直接摆放建筑，不直接规划小镇。
宠物和未来伴生体是后置生命事件，不是默认开局资产。
FormalWorldView 只能只读 FormalVisualModel，不能生成 placement、actor、world object。
1.2 本版新增的核心结论
世界不是“自由随机地图”，而是“规则生态世界”：沙漠、绿洲、森林、草地等地貌必须有各自资源、气候和建设限制。
资源不是无限货币，而是世界状态的一部分：固定存量、可消耗、可恢复、可转换、可枯竭，也可在条件满足时产生新资源。
自动建设不是一次性事件，而是长期循环：观察 -> 判断 -> 计划 -> 消耗资源 -> 生成 MapDiff -> SafeApply -> 维护/衰退。
家园、社区、小镇不是玩家规划出来，而是多个自主体在规则、资源和关系网络中长期形成。
房子不是固定模型：房屋类型、位置、扩建方式、装饰风格、维护优先级应由管家人格和资源环境共同决定。
2. 产品本质与品类定位
AI-PET-WORLD 不应被定义成普通“宠物游戏”“建造游戏”或“算命产品”。它更接近一个人格驱动的自主世界模拟系统。它的独特性不是单一 AI 对话、不是地图美术，也不是宠物养成，而是把用户生命信息映射成管家人格，再由管家和世界规则共同推动世界长期演化。
本产品的前台表达应是：输入你的生命信息，生成一个属于你的 AI 管家和第一片世界；它会自己生活、整理、建设、维护，并在未来决定是否接纳新的生命。
2.1 产品护城河
3. 世界观与角色关系
AI-PET-WORLD 的世界由四层构成：玩家源头层、人格自主层、规则生态世界层、只读表现层。任何实现都必须尊重这四层的边界。
3.1 玩家不是建造者
玩家的作用是“世界源头”和“观察者”。玩家可以创建世界、观察世界、通过有限方式表达偏好或进行关系回应，但不能像传统经营游戏一样直接拖拽建筑、点击建造、安排 NPC 行为。
3.2 管家是自主管理者
管家不是传统游戏的功能 NPC。管家是由玩家生命信息映射出的自主管理者，具有建设倾向、维护倾向、资源偏好、关系态度、视觉审美和生活节奏。管家的任务不是替宠物服务，而是维护世界、形成家园、理解资源、记录变化并根据条件决定是否开放新的生命关系。
管家可以观察：资源是否短缺、地面是否衰退、边界是否需要维护、住所是否需要扩建。
管家可以建设：住所、路径、储备区、安静区、照护区、边界、社区节点。
管家可以维护：道路、房屋、资源点、自然边界、公共空间。
管家可以等待：资源不足、风险过高、关系事件未成熟时，不主动扩张。
管家可以拒绝或延迟接纳宠物：宠物不是默认路线。
4. 规则生态世界定义
世界是自主的，但不是混乱的。世界有地貌规律、资源约束、气候条件、建设限制和生态反馈。沙漠就是沙漠，绿洲就是绿洲；不同地貌不会因为 UI 想好看就随意改变自己的资源逻辑。
“自主世界”不是指无规则随机，而是指在规则约束下由内部状态推动演化。世界的每一次变化都应该能够回答五个问题：为什么发生、由谁发起、消耗了什么、改变了什么、是否通过审计。
4.1 世界规则不是背景说明，而是产品本体
如果一个世界地貌、资源和建设只是写在文案里，代码仍然用固定模板摆放对象，那就不符合本产品。规则必须进入数据结构和运行循环，成为可执行逻辑。

-> VisualProjection
4.2 世界状态的基本守恒原则
5. 地貌、生物群落与生态规律
地貌是世界规则的上层约束。家园、社区和小镇不是漂浮在空白地图上的建筑，而是在特定地貌中生长出来的结果。MVP 可以先从草地/自然边界开始，但架构必须支持沙漠、绿洲、森林、湿地、山地、海岸等扩展。
5.1 地貌规则字段建议
6. 资源系统：有限存量、消耗、恢复与新资源产生
资源系统是世界自主性的基础。资源不是 UI 数值，也不是无限货币。资源是世界状态的一部分，拥有存量、容量、恢复速度、来源、去向和衰退影响。世界中的建设、维护、生命事件和社区扩张都必须依赖资源。
6.1 资源守恒与再生
世界资源既有固定数量，也能在符合生态规律时产生新的资源。这里的“新资源”不是凭空生成，而是由地貌、天气、时间、设施和生命行为共同作用产生。
6.2 ResourceTransaction 字段
7. 玩家角色：世界源头而非建造者
玩家的输入是世界的源头，但玩家不是传统游戏中的建造者、市长、饲养员或上帝手。玩家的核心体验是观察“这个由我生命信息启动的世界如何自己发展”。
8. 管家角色：玩家生命信息映射出的自主管理者
管家是 AI-PET-WORLD 的第一主角。宠物可能出现，也可能不出现，但管家必然存在。管家不是宠物服务员，而是世界管理者、记录者、建设者、维护者和关系判断者。
8.1 管家人格向量
9. 人格驱动引擎：从生命信息到行为偏好
生命信息人格引擎是内部算法层。前台不应展示命盘、星曜、宫位等原始术语。工程上应把这些信息转为可运行的行为向量、建设向量、关系向量和视觉倾向。

9.2 前台隐藏命理标签的要求
正式 UI 只展示“性格结果、生活倾向、建设偏好、管家解释”，不展示原始命理术语。
Debug 页面可以显示内部调试标签，但必须与正式 /world 分离。
用户文案应使用“生命信息人格引擎”“专属管家人格”“世界源头信息”等表达。
内部算法可以保留命理人格核心，但输出必须转译为工程字段。
10. 世界生成：非固定、可复现、可审计
世界生成不是固定模板，也不是无规则随机。正确模式是：规则约束 + seed 稳定性 + 人格差异 + 资源状态 + 地貌限制 + 建设和事件长期介入。

-> HomeMapState
-> RenderableWorldSnapshot
-> FormalVisualModel
10.1 Recipe 的正确定位
Scene Recipe 可以存在，但不能变成最终固定画面。Recipe 应定义“候选关系、功能需求、空间约束、连接意图和可用对象类型”，而不是写死每个区域中心点和固定布局。
10.2 非固定布局验收标准
11. HomeMapState 与世界事实容器
所有正式世界事实必须进入状态容器。任何无法进入 HomeMapState、RegionState、ResourcePoolState、SettlementState 或 MapDiff 的内容，都不能被正式画面当作存在。
11.1 HomeMapState 建议字段
12. MapDiff / EventLog / SafeApply
世界变化不能直接改对象。建设、维护、资源变化和生命事件都应该先产生候选 diff，再通过审计和 SafeApply 进入正式状态。
Intent
-> Plan
-> CandidateDiff
-> DiffAudit
-> SafeApply
-> nextHomeMapState
-> Snapshot Refresh
-> FormalVisualModel Refresh
-> Player-facing Log
13. 自动建设系统：家园、社区、小镇
自动建设系统是产品核心之一。它不能被做成“玩家点击建造”。建设由管家和未来社区成员根据人格、资源、地貌、需求、事件和长期目标自主发起。
13.1 自动建设闭环
WorldLoop Tick
-> Observe HomeMapState / ResourcePool / Biome / Events
-> Build ButlerIntent
-> Build ConstructionPlannerInput
-> Generate ConstructionPlan Candidates
-> Select Plan by personality + resource feasibility + urgency
-> Execute Plan Candidate
-> Generate MapDiff + ResourceTransaction
-> SafeApply
-> Update HomeMapState
-> Refresh Snapshot / FormalVisualModel
-> Build ButlerExplanation / WorldLog / P-Phone
13.2 建设不是一次性“完成”，而是长期维护
AI-PET-WORLD 的建筑应该会老化、需要维护、可能被天气或资源短缺影响。这样世界才像活的，而不是一次摆放完就永远存在。
14. 房屋偏好与建筑风格映射
“他们会建造自己喜欢的房子”必须被工程化为 HousePreference 和 HouseArchetype，而不能停留在文案。不同管家人格应影响房屋类型、空间组织、扩建节奏、材料选择、装饰风格和维护优先级。
14.1 HousePreference 字段
15. 维护系统与长期衰退/修复
维护系统能让世界看起来持续运行。建筑、道路、资源点、自然边界、公共设施都应该有耐久、清洁、可用性和维护成本。
16. World Loop 与离线运行
World Loop 是世界活着的证据。MVP 可以先用手动 Tick 或 preview tick，但最终必须支持稳定的时间推进和离线结算。离线结算不是随便补结果，而是按规则压缩模拟。
16.1 离线运行原则
离线不是直接跳到“更大房子”，而是按时间片执行简化规则。
离线建设必须消耗资源，并生成可审计摘要。
离线期间重大事件可以生成候选，但高风险关系事件需要玩家回访后确认。
离线结算必须保留 WorldLog，让玩家知道世界不是凭空变化。
17. LifeEvent 与宠物/伴生体后置入口
宠物不是默认开局，也不是所有用户都会进入的分支。宠物和伴生体属于 LifeEvent 系统，在世界稳定度、资源、管家关系倾向、玩家回应和事件条件满足后，才可能进入。
17.1 宠物前置禁止清单
禁止初始世界默认生成 pet actor。
禁止默认 pet bed、pet_arrival、pet_rest。
禁止用“照护区”暗示宠物已存在。照护区是基础生活支持，不等于宠物设施。
禁止宠物说人话。宠物事件文本应是动作、状态、环境反馈。
禁止所有管家默认选择养宠物。
18. Formal Visual Generation Layer
视觉层是事实投影，不是事实生成。FormalVisualModel 是正式主视觉模型容器，FormalWorldView 只读渲染。美术资产、CSS、SVG、PNG 都不能反向决定世界对象是否存在。
HomeMapState / WorldState
-> VisualState / RenderableWorldSnapshot
-> FormalVisualGenerator
-> FormalVisualModel
-> FormalWorldView read-only render
19. MVP 功能边界与不可做事项
MVP 不是完整商业产品，但必须证明核心闭环：输入生命信息 -> 生成管家和初始世界 -> 世界事实进入 HomeMapState -> 管家产生建设倾向 -> MapDiff/SafeApply 变更世界 -> FormalVisualModel 展示 -> 日志/解释可读。

25. 最终结论
AI-PET-WORLD 的复杂性不是负担，而是产品优势。这个项目的核心不是单点功能，而是一套“人格 -> 规则 -> 资源 -> 自主建设 -> 世界事实 -> 可审计演化 -> 只读视觉表达”的完整系统。
最终产品愿景：一个由玩家生命信息启动、由管家人格和世界规则驱动、拥有资源循环和生态限制、能自主建设家园/社区/小镇的 AI 生命世界。

附录 D：世界规则引擎详细规格
本附录把“世界有规律”拆成可以工程实现的规则组。每条规则都应能被序列化、审计、测试，并且能在 world-loop 中按优先级执行。规则不是一段自然语言说明，而是可以参与计算的结构。
附录 D.1 规则优先级与冲突解决
当多个规则冲突时，AI-PET-WORLD 必须优先保护世界一致性。比如管家想扩建住所，但沙漠地貌缺水、材料不足，则 ConstructionPlan 可以生成“等待/准备资源”的计划，而不能直接生成完成后的房子。

附录 F：资源循环详细规则
资源循环必须让世界像地球状态一样运行：资源有初始存量，有固定容量，有自然恢复，有人为消耗，有转化，有衰退。资源循环不是经济系统的装饰，而是管家决策和世界演化的底层约束。

以下样例用于产品、测试和视觉验收。它们不是固定模板，而是“相同世界规则下的不同人格路径”。
附录 I：家园到社区到小镇的演化细节
家园、社区、小镇的演化不能被设计成玩家手动升级。它应当由资源网络、空间压力、关系记忆、公共需求和群体建设行为共同推动。
附录 J：用户体验完整流程
产品复杂不代表前台复杂。用户体验应该克制、安静、有观察感。用户不需要理解所有状态容器，只需要感到“这个世界在自己运行，而且与我有关”。

复杂系统最容易失败的地方不是类型错误，而是“看起来可以运行，但产品哲学已经错了”。以下失败案例必须写入开发复盘和 Code Review。
附录 P：MVP 页面与交互详细设计
MVP 页面应围绕“观察世界”设计，而不是围绕“操作世界”。页面可以有按钮，但正式用户按钮不能变成建造、摆放或强制行为。
附录 Q：MVP 到产品化的体验差距清单
MVP 工程闭环通过不等于产品可上线。以下差距必须提前记录，避免把“能 build”误认为“能给用户体验”。
附录 R：分模块开发详细任务表
附录 S：产品表达策略
产品对外表达应该降低“命理”标签，强调“专属 AI 管家”“自主运行世界”“世界会自己建设和维护”。内部文档可以保留命理人格核心，但用户不需要看到算法术语。
附录 T：最终开发判断句
后续每当出现分歧时，用以下判断句检查是否走偏。
如果一个对象没有进入 HomeMapState 或后续状态容器，它就不应该出现在正式世界里。
如果一个建设动作没有资源消耗、可行性判断和 SafeApply，它就不应该改变世界。
如果一个视觉效果不能追溯到 FormalVisualModel，它就只是表现，不是事实。
如果一个宠物没有经过 LifeEvent / CompanionDecision / accept_companion，它就不应该存在。
如果一个地图所有玩家都差不多，它就没有体现人格驱动和非固定生成。
如果玩家能直接建造房子，产品哲学就被破坏。
如果资源无限或凭空出现，世界就不再像真实生态系统。
