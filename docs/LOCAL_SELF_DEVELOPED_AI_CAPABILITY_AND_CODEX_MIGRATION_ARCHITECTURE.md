## 0. 业务说明层

### 0.1 业务背景

当前项目中的需求理解、任务拆解、代码编写、编译测试、故障诊断、模型训练协助、证据核验和文档维护，仍有一部分依赖Codex等外部智能体。聊天断线、窗口切换、外部服务不可用或上下文丢失，都可能降低工作连续性。

项目需要建设的不是一个只会画图的模型，而是一套受项目业务目标与能力版本治理、能够理解项目资料、自主执行合同任务、保存正式证据、处理失败并持续演进的本地智能工作系统。

### 0.2 业务定义

本业务定义为：

> 把当前由Codex协助完成的项目专属工作能力，按照可验证、可回退、逐项机器验收的方式迁移给本地自研AI和本地程序；Owner只需通过本地控制台设定或调整业务目标，本地系统自行形成能力版本并独立完成研发与运行闭环，Codex只保留可选的只读监督职责。

迁移对象是项目工作能力、流程合同、工具接口和验收方法，不是复制Codex的模型权重、内部系统、隐藏提示词或服务端能力。

### 0.3 “本地自研AI系统”的组成

本文中的本地自研AI不是一个万能模型，而是以下组件共同组成的系统：

```text
本地自主运行核心 / Owner只读与紧急控制台
-> 项目知识与文档系统
-> 需求理解与任务规划器
-> 合同、资源与风险门禁
-> 本地AI模型与专用算法
-> 代码/文件/构建/测试工具执行器
-> 数据、训练、验证与推理系统
-> 审核、失败分析与回归系统
-> 资产、版本、证据与查询系统
-> 只读监控与告警系统
```

模型负责理解、预测、规划或生成；本地程序负责确定性校验、权限控制、工具调用、状态持久化和安全停止；二者不得混写为同一个主体。

#### 0.3.1 统一主体术语

| 术语 | 固定含义 | 不得误写为 |
|---|---|---|
| 本地自研AI模型 | 在本地训练和运行，负责学习、推理、生成、人物感知、目标形成与决策的模型 | 普通脚本或整个系统 |
| 本地程序 | 负责训练调度、模型调用、Runtime执行、确定性门禁、证据保存和安全停止的程序 | 会自主学习的模型 |
| 本地自研AI系统 | 本地自研AI模型、本地程序、数据、控制台、资产与证据系统组成的整体 | 单一模型或单一训练脚本 |
| 项目所有者 | 设定业务目标、观察系统、暂停或紧急覆盖，并处理外部许可/付费/不可恢复边界 | 本地AI日常训练、验证或发布审批员 |
| Codex | 当前负责系统代码建设、复杂诊断与有界修复，未来逐步降为只读核验 | 正式系统记录或运行时必要依赖 |

任何涉及模型生产的正式表述必须写明“本地自研AI训练系统”，不能只写“本地程序”。本地程序是确定性执行载体，训练、验证和审核的业务对象及能力主体是本地自研AI系统。

### 0.4 业务目标

1. 项目知识本地化：本地系统能读取权威文档、识别优先级、发现冲突并保持项目记忆。
2. 任务理解本地化：把自然语言目标转成有范围、有门禁、有验收的任务合同。
3. 软件工作本地化：逐步承担代码创建、修改、重构、审查、编译、类型检查、测试和差异核验。
4. 模型生产本地化：独立完成数据选择、训练、验证、影子推理、审核和资产管理。
5. 故障处理本地化：自动收集证据、定位原因、提出最小修复、验证回归并在失败时停止。
6. 项目运营本地化：由本地程序自动记录状态、Token、资源、事件、内部票据、决定和恢复点。
7. 外部依赖可退出：关闭Codex或丢失聊天历史不会中断正式业务流程。

### 0.5 三类主体的职责

| 主体 | 正式职责 | 永久限制 |
|---|---|---|
| 项目所有者 | 设定或改变业务方向，观察、暂停和紧急覆盖系统，处理外部许可、付费服务和不可恢复操作 | 不承担日常审批或逐版本签署 |
| 本地自研AI与本地程序 | 在生效合同内理解、计划、实现、训练、验证、发布、记录、阻断、恢复和持续演进 | 不得改变长期业务事实或静默放宽安全与审核边界 |
| Codex等外部智能体 | 当前按明确命令协助建设、诊断和核验；成熟后只读监督 | 不得成为系统记录、长期记忆或正式授权机关 |

### 0.6 首个落地模块与长期范围

AI Painter是第一套落地和验证本框架的业务模块，因为它已经具备数据、训练、验证、审核、控制台和证据链。它不是永久范围。后续迁移应覆盖项目文档、软件工程、AI管家、世界事实、运行时接口和其他本地模型，但每个模块必须单独通过迁移门禁。

当前泰国Sakaerat / Wang Nam Khiao真实测量数据只用于MVP冷启动和训练链验证，不构成长期地理边界。未来数据必须按地区独立建立来源、许可、版本、事实派生和验收合同。

#### 0.6.1 当前MVP能力筛选

长期框架保留Codex职能迁移方向，但当前MVP只要求本地自研AI完整展现游戏核心业务，不要求它现在能够开发自己的代码。

当前MVP固定包含：

| 能力 | MVP必须达到的结果 | 当前执行主体 | 控制主体 |
|---|---|---|---|
| 人物人格 | 根据紫微斗数、八字和映射模式形成稳定人格倾向 | 本地自研AI模型与人格程序 | 项目所有者定义业务规则 |
| 人物记忆与感知 | 保存经历并读取位置、环境、资源、时间和世界事件 | 本地自研AI模型 + 本地记忆程序 | 项目所有者审核边界 |
| 动机、目标与自主决策 | 根据人格、记忆和世界状态形成目标并选择行动 | 本地自研AI模型 | 项目所有者保留最终控制权 |
| 世界事实生成 | 生成地形、水文、气候、生态、资源和连接事实 | 本地自研AI系统 | 长期业务、来源许可和WorldFacts合同约束 |
| 完整地图生成 | 根据世界事实和结构条件生成完整游戏地图 | 本地自研AI Painter系统 | 自主训练、机器审核、能力发布、Runtime发布与回退 |
| 地图语义与动态运行 | 提供通行、碰撞、道路、水体、对象语义并推进时间、天气和生态 | 本地程序与游戏Runtime | 已发布能力版本与Runtime发布门约束，单次运行不逐次请求Owner授权 |
| 人物—世界闭环 | 人物感知世界、自主行动、Runtime产生合法变化、记忆更新并继续决策 | 本地自研AI系统 + 游戏Runtime | 项目所有者监控与暂停 |
| 状态持久化 | 保存人物、世界、时间、事件和恢复点 | 本地程序 | 项目所有者管理存档 |
| 训练与验证 | 本地完成自研AI模型的数据选择、训练、Checkpoint保存、训练后验证、机器审核、失败隔离、Token统计和证据保存 | **本地自研AI训练系统（本地自研AI模型 + 本地训练、验证和审核程序）** | **项目所有者决定新的训练计划与能力版本发布；包内训练、验证、审核和记录由本地系统闭环** |
| Owner观察与紧急控制 | 在本地后台查看状态、暂停或紧急覆盖；可以改变业务目标但不逐任务审批 | 本地控制台与证据系统 | 项目所有者 |

当前MVP的完整游戏闭环固定为：

```text
创建世界与WorldFacts
-> 生成完整地图和运行语义
-> 创建具有稳定人格和记忆的人物
-> 人物感知世界并自主形成目标
-> Runtime执行合法行动
-> 世界事实发生变化并保存
-> 人物感知新的世界状态并继续决策
```

当前Codex仍可在Owner明确交付的外部任务范围内完成系统代码建设、编译测试、文档维护和复杂诊断。该外部任务边界不等于本地自研AI的运行边界；随着能力迁移，日常训练、验证、审核、发布、Runtime和记录不再依赖Codex。

当前MVP暂不实施本地AI自动写代码、自动重构、通用开发任务规划、自动维护全部文档、完整接管Git、多国家并行生产、完整城市社会经济系统或Codex全面退出。主体架构保留这些长期能力，不代表当前模块范围已经包含它们。

### 0.7 业务闭环

正常闭环：

```text
当前生效业务目标或世界事件触发任务
-> 本地系统读取权威资料并生成任务合同
-> 合同、数据、资源与风险预检
-> 本地程序自主执行
-> 自动测试/验证/审核
-> 不可变保存资产和证据
-> 机器决定发布、回退、进入下一阶段或失败关闭
-> Owner控制台只读展示，必要时可暂停或紧急覆盖
```

失败闭环：

```text
发现错误或门禁失败
-> 立即停止超出当前合同的后续动作
-> 保存输入、环境、日志、失败码和影响范围
-> 本地诊断并提出最小修复合同
-> 合同内基础设施问题由本地程序有界恢复；能力或业务变化进入项目级决定
-> 有界修复与正反回归
-> 成功则恢复，失败则保留证据并继续阻断
```

### 0.8 业务成功标准

最终成功不是“本地模型能回答问题”或“能生成一张图”，而是：本地系统能够自主完成正式业务任务和能力演进，解释计划、限制和结果；失败可以安全停止与恢复；正式资产可追踪；关闭Codex不影响业务连续性；Owner只处理业务目标、观察、紧急控制及外部边界。

### 0.9 本地持续执行与完整业务闭环

AI Painter 的长时间训练、生成和审核必须由独立于Codex窗口的本地持续执行器承担。任务包在启动前列明能力版本、阶段顺序、运行器、输出目录、前序成功条件、停止规则和恢复边界；本地执行器随后持续推进，不因聊天关闭而停止。

每个阶段在开始前必须同时包含训练后验证、机器审核、失败隔离、Manifest、Finalization、终态与治理记录。训练自然完成后，这些内部动作由本地自研AI训练系统连续执行，不依赖Codex在线，也不形成新的人工操作点。若内部动作因程序缺陷失败，系统保存基础设施失败，并在能力版本允许的范围内完成有限恢复。不得把程序内部流程拆分成反复向Owner请求授权的聊天步骤。

技术上，该能力由五层组成：能力版本定义固定阶段与禁止边界；本地规划器物化精确执行计划；状态机签发内部一次性任务票据；持续执行器逐阶段验证、执行、等待运行器自然退出并检查正式终态；任务胶囊、事件账本与SQLite保存执行证据。内部票据只负责幂等与证据追溯，不代表从Owner借来的运行权限。

持续执行状态机固定为：

```text
能力版本与精确计划已物化
-> Smoke独立执行与终态检查
-> Stage 0独立消费与终态检查
-> Stage 1独立消费与终态检查
-> Stage 2独立消费与终态检查
-> Stage4完成并更新为4/5（80%）
```

上图每个“终态检查”均包含训练、固定预览复现、验证、机器审核和终态落盘的同包闭环；它不是仅检查训练进程退出码。

任何阶段真实失败、证据冲突或输出目录冲突时，本地执行器必须停止当前路线；不得无限重试、降级审核门槛或改用历史失败运行。它可以按合同选择另一条已声明的有界路线；触及长期业务、许可、付费或不可恢复边界时生成业务边界报告并等待业务方向。正式业务与验收合同见[AI Painter正式主体规格](game-world-generation/AI_PAINTER_FORMAL_IMPLEMENTATION_SPEC.md)。

### 0.10 AI Painter原生自主判断能力

本地AI Painter必须从“Codex解释证据、人工逐步推进”迁移为“本地程序和本地模型完成正式闭环”。第一阶段由确定性程序承担证据完整性验证、状态转换、固定审核、有限选项裁决、失败关闭和治理记录；生成式本地模型负责问题理解、候选解释和修复建议，但不能覆盖机器证据或绕过确定性门禁。

迁移后的三层责任固定为：

1. 项目所有者设定业务目标、观察、暂停或紧急覆盖，不审批日常能力版本和路线；
2. 本地程序依据生效业务合同签发和消费内部任务票据，执行确定性闭环、形成能力版本并在不唯一时失败关闭当前路线；
3. 本地模型逐步承担理解、规划、诊断和建议，并受程序门禁约束；
4. Codex负责研发期代码建设、复杂诊断和有界修复，不能成为运行、审核、发布或记录的必要依赖。

内部任务票据只在同一执行包、同一证据、同一能力版本和同一程序血缘中有效。代码、模型、数据或阈值变化必须形成新的能力版本；真实失败训练不能由内部票据无限重试。该限制用于阻止“自主判断”退化为程序自我扩权。

## 2. 核心战略

核心战略是持续扩充本地系统的知识、规划、软件工程、数据、训练、验证、生成、审核、自动化、治理和运行接口能力，使外部智能体依赖随本地能力成熟而逐项下降。

必须同时建设五条链：

| 建设链 | 目标 |
|---|---|
| 知识链 | 权威文档、代码、数据合同和历史证据可检索、可引用、可发现冲突 |
| 执行链 | 任务计划、权限、工具、编译、测试、训练和推理可由本地程序运行 |
| 质量链 | 静态检查、测试、验证、审核、失败学习和回归闭环 |
| 证据链 | 输入、输出、版本、哈希、资源、决定和状态全部可追踪 |
| 控制链 | 项目所有者直接控制，系统不能自行扩权，Codex不是必要依赖 |

## 3. 最终运行模式

```text
项目所有者设定业务目标 / 世界事件触发任务
-> 本地知识系统提供相关事实和规则
-> 本地规划器生成可解释任务计划
-> 能力门禁标明可执行、需变更和禁止范围
-> 本地执行器完成合同内工作
-> 本地验证器独立检查
-> 证据系统自动入账
-> 本地系统自主发布、回退或失败关闭
-> 触及长期业务或外部边界时报告给项目所有者
```

正式流程不得依赖聊天历史、Codex在线状态、外部智能体临时记忆或未落盘的口头状态。

## 4. 权力、职责与隔离边界

### 4.1 项目所有者

项目所有者永久保留业务方向、暂停、紧急覆盖、外部付费/法律承诺和不可恢复破坏性操作的控制权。本地系统在生效业务、来源、资源和安全合同内自主选择数据、形成新能力版本、训练、验证、审核、发布、生成RuntimeFrame和运行世界；项目所有者不承担逐任务或逐版本操作员职责。

### 4.2 本地AI模型

模型可以理解需求、检索知识、提出计划、生成候选代码或图像、预测风险和辅助诊断。模型输出默认是候选，不自动成为事实、正式代码、正样本、正式能力版本或世界状态。

### 4.3 本地程序与工具执行器

本地程序负责身份校验、能力版本哈希、文件边界、命令白名单、环境快照、任务锁、超时、回滚、测试、证据写入和状态机。确定性约束优先由程序执行，不交给概率模型自行保证。

### 4.4 游戏Runtime

游戏Runtime负责合法世界状态推进。AI模型只能通过版本化合同提供经过验证的候选输入；不得直接改写世界事实或越过RuntimeFrame与审核门禁。

### 4.5 Codex

Codex当前可以在项目所有者明确要求下协助实现和诊断。每项本地能力达到迁移标准后，Codex对该能力降为只读监控；不得用“整体系统尚未完成”作为继续代执行已成熟能力的理由。

## 5. 总体系统架构

| 层级 | 核心职责 | 主要产物 |
|---|---|---|
| 所有者交互层 | 业务目标、观察、暂停、紧急覆盖和外部边界处理 | business direction / emergency control |
| 项目知识层 | 文档、代码、数据和证据索引 | 带来源的检索上下文 |
| 需求与规划层 | 目标分解、依赖、风险、验收 | task contract / plan |
| 策略与权限层 | 权限范围、破坏性动作、秘密和资源门禁 | policy decision |
| 执行工具层 | 文件、代码、构建、测试、数据和系统工具 | execution event |
| 模型生产层 | 数据集、训练、验证、推理和生成 | model asset / candidate |
| 质量与失败层 | 审核、测试、对比、失败分类和回归 | review / failure / repair contract |
| 资产与证据层 | 版本、哈希、血统、Token、资源和索引 | immutable evidence |
| 监控与治理层 | 状态、告警、能力成熟度和迁移状态 | dashboard / registry |

各层必须通过机器可读合同连接。任何页面文字、模型回答或聊天结论都不能代替正式状态文件。

## 6. 数据、知识与世界事实框架

### 6.1 数据类别

系统应区分项目文档、源代码、测试、真实测量数据、世界事实、条件包、训练RGB、失败样本、模型资产、运行事件和游戏状态。不同类别必须有独立资格和保留规则。

### 6.2 来源与原创性

“项目自研代码”“本地运行模型”“自主采集数据”“自主训练权重”是四个不同声明。使用开源依赖、基础模型、外部数据或AI辅助冷启动内容时，必须分别记录来源、许可、版本和限制，不能统一宣称为完全独立原创。

不得复制Codex内部实现。可以把项目已经明确的工作步骤重构为本地程序、规则和自研接口，并对实现做原创性、许可证和依赖审计。

### 6.3 训练资格

AI辅助冷启动数据、程序生成数据和合成RGB都不自动获得正向训练资格。正式训练至少需要来源许可、条件身份、数据血统、机器审核、去重、split隔离、不可变哈希和数据版本机器发布身份。

失败内容必须保留并与正向容量隔离。训练、validation、challenge和regression之间必须防止相同来源窗口、共享骨架、变换派生或语义近邻造成泄漏。

### 6.4 MVP泰国数据定位

泰国Sakaerat / Wang Nam Khiao包仅为当前MVP启动包，用于验证真实事实派生、23通道、完整地图训练和审核闭环。数据、模型和门禁架构不得固定为单一国家；新地区必须建立自己的`RealEarthRegionSourcePackage`。

### 6.5 项目知识系统

本地知识系统必须保存文档优先级、时间戳、适用范围、引用关系和已废止状态；回答或规划时必须给出依据文件，发现冲突时阻断而不是任选一个结论。

## 7. 本地AI能力框架

### 7.1 文档与知识理解

- 按权威索引读取相关文档，不默认全库灌入。
- 识别当前规则、历史证据、锁定规格和机器合同。
- 进行引用追踪、重复检测、过期状态识别和冲突报告。
- 将任务结论自动写入指定系统记录，不依赖Codex补写。

### 7.2 需求理解与任务规划

- 把所有者目标转成范围、输入、输出、禁止项、依赖、风险和验收标准。
- 区分只读检查、可逆修改、破坏性动作和外部状态变更。
- 输出计划但不把计划当证据；超出项目合同的能力不得执行，合同内能力不等待人工授权。
- 支持暂停、恢复、取消、重试上限和失败即停。

### 7.3 软件工程能力

- 搜索与理解代码、定位调用链和影响范围。
- 创建、修改、重构和审查代码，保持目录、命名和模块边界。
- 自动运行格式、类型检查、编译、单元测试、集成测试和回归测试。
- 读取错误日志并形成证据化根因，不用无依据试错代替诊断。
- 生成最小补丁、检查Git差异、识别用户已有改动并支持回退。
- 禁止越过工作区、泄露秘密、静默覆盖或执行超出合同的破坏性命令。

### 7.4 数据与条件构建

- 读取来源包和世界事实，构建可追踪语义条件。
- 验证道路、水文、岸线、生态、季节、边界和对象关系。
- 检查历史大骨架、局部细节和跨模态重复。
- 输出带身份、版本、来源、资格和哈希的Manifest。

### 7.5 模型训练

- 训练能力的正式主体统一称为“本地自研AI训练系统”，由本地自研AI模型以及本地训练、验证、审核和证据程序共同组成。
- 本地自研AI负责在生效业务合同内选择新的模型、数据版本、训练计划和审核实现，形成隔离能力版本并完成机器验证、发布或回退；Owner不逐版本批准。
- Codex当前只负责训练系统代码建设和复杂故障修复，不参与日常训练任务的正式执行；该职责以后再按能力验收逐项迁移。
- 选择任务、数据、模型、Stage、超参数和父Checkpoint。
- 在启动前验证实际样本、split、来源、显存、时间和Token预算。
- 支持排队、任务锁、安全终止、断点恢复和失败自动停止。
- 自动保存epoch、指标、预览、Checkpoint、血统和环境快照。

### 7.6 训练后验证

- 验证实际样本、split和Checkpoint父子链。
- 在未见数据、多种子和固定条件上验证控制能力与泛化。
- 检查过拟合、数据泄漏、结构响应、纹理质量、重复和稳定性。
- 训练完成不等于验证通过；验证通过也不等于该能力版本已经完成发布验收。

### 7.7 推理与生成

- 先以影子模式运行并与正式通道对比。
- 输出完整候选、条件响应证据、种子、模型和资源记录。
- 未获资格的模型不得进入正式生成；生成结果不得自动成为正样本或RuntimeFrame。

### 7.8 审核、失败学习与修复

- 执行来源、合同、技术质量、语义对齐、历史重复和业务适用性审核。
- 保存失败输入、失败码、位置、版本、日志、可选业务方向和影响范围。
- 本地失败学习程序必须按时间顺序归一化失败证据，区分持续失败、逐步收敛、中途出现、消失后复发和终态稳定性不足；不得把所有失败图当作同一种根因。
- 根因只能作为带置信度、证据码、Epoch、来源路径和哈希的候选结论；缺少证据时必须标记未知，禁止把外部智能体的聊天判断写成机器事实。
- 本地系统必须形成机器可读的有界修复合同，至少包含允许修改目标、禁止修改项、训练配置补丁提案、正向回归、反向回归、回退点、能力版本状态和是否已经应用。
- 训练配置补丁可以由本地系统提出；涉及模型、数据、Loss、阈值或训练计划的补丁必须进入新的能力版本变更流程。固定验证、机器审核、只读分析、失败关闭和终态记录随当前执行包自动完成。
- 对象语义修复不得只使用合并后的对象总分；训练器必须至少能分别记录tree、rock、vegetation对象通道Loss，并保留对应条件通道、优化步、Epoch和配置版本，以便定位不同对象学习速度。
- 道路修复必须分别监督条件包内的道路覆盖和条件包未声明的地图边界；任何未声明边界接触不得被普通边界Loss平均掩盖。
- 单次末段通过不得证明修复稳定。候选Smoke必须使用固定末段检查点并连续三次通过全部既有机器门禁；审核阈值不得因为修复而降低。
- 本地系统生成的候选配置必须与正式配置隔离，标记未激活、未训练和合同边界；CPU合成回归只证明Loss、门禁和梯度合同可工作，不证明模型质量或训练资格。
- 修复后的闭环必须回到同一拒绝码和同一证据合同执行正反回归，防止同类错误复发，同时证明审核门槛没有被降低。
- 不得通过降低门槛、删除失败证据或重复生成掩盖问题。

### 7.9 项目记录与恢复

- 自动写任务、内部票据、事件、决定、Token、资源、资产和当前指针。
- 使用原子锁、幂等身份和不可变记录避免重复执行动作。
- 支持从明确恢复点继续，并能证明恢复前后环境和父资产一致。

## 8. 本地任务操作台框架

操作台是本地系统任务规划和Owner业务目标/紧急控制的入口，监控台不是写操作入口。

操作台至少支持：文档整理、代码实现、编译测试、数据构建、模型训练、训练后验证、影子推理、回归测试、模型对比和失败修复。每次启动前必须展示任务范围、输入与排除项、程序版本、环境、预计资源、风险、回退点、当前阻断以及明确不包含的后续权限。

本地规划器依据生效业务合同建立唯一任务ID、任务合同哈希和内部幂等票据；任务参数一旦启动不得静默变化。Owner不需要逐任务确认。

失败修复任务必须在操作台内显示本地程序自动生成的时间轨迹、问题聚类、根因候选、置信度、证据路径、训练配置补丁提案和正反回归合同。操作台必须区分“提案”“机器验证中”“已激活版本”和“训练中”；本地系统只有完成版本化预检和回归后才能应用配置，不能把提案直接显示为已应用。该状态转换由机器证据决定，不等待Owner审批。

## 9. 只读监控台框架

监控台只展示当前任务、计划步骤、状态、进度、参数、日志、测试、Stage、Epoch、Checkpoint、CPU、内存、GPU、显存、磁盘、网络、Token、成本、失败码、当前门禁和能力迁移状态。

历史运行按任务ID或Run ID独立查看。页面不得伪造未保存的中间图、诊断图或指标；只允许展示本地程序已自动保存并绑定身份的证据。监控台不得修改参数、启动任务或绕过合同门禁。

## 10. Token、时间与资源计量

图像扩散训练的本地潜空间Token固定定义为“一个去噪样本前向处理的一个潜空间位置”。它不是NLP Token，也不是API计费Token。代码模型或其他本地模型必须建立各自可验证的计算单位，不得混用名称。

每次运行至少记录：样本呈现、优化步、模型前向、验证轨迹、潜空间或上下文处理量、生成像素、运行时间、CPU、内存、GPU、显存峰值、磁盘读写、网络、Checkpoint大小和能耗可得值。

外部服务Token和费用只有在服务商返回权威usage时才记录；禁止按字符、时间、图片数或GPU用量估算外部Token。

## 11. 资产、版本、环境与可复现性

正式资产必须具有唯一ID、时间、来源、版本、SHA-256、状态、父级、资格、归档位置和失败原因。代码任务还必须记录Git基线与差异；模型任务必须记录数据Manifest、模型配置、随机种子、依赖锁、驱动、CUDA、硬件和Checkpoint血统。

正式资产不得无记录覆盖。升级必须定义兼容性、迁移、回退和旧版本保留规则；应对灾难性遗忘、模型退化、依赖漂移和存储损坏设置回归与恢复验证。

## 12. 游戏世界与Runtime接口边界

AI Painter的完整RGB只是世界视觉生产链的一项资产，不是动态世界本身。本地模型可以输出经合同验证的语义层、结构候选、视觉候选或RuntimeFrame候选；世界Runtime负责碰撞、交互、时间、生态、角色和合法状态推进。

模型不得直接写`/world`。任何进入Runtime的产物都必须具有WorldFacts来源、接口版本、语义层、审核结果、机器能力发布身份和回退点；第一版与重大能力版本变更使用同一完整机器发布门，单次候选由机器审核和Runtime发布门决定，不逐张或逐版本请求Owner授权。

## 13. 能力成熟度框架

成熟度必须按“具体能力”分别记录，不能用一个L5标签概括整个系统。

| 等级 | 定义 |
|---|---|
| L0 | 主要由人工或外部智能体执行，本地无可靠记录 |
| L1 | 本地能够完整记录，但不能执行 |
| L2 | 本地可辅助执行，关键步骤仍依赖外部能力 |
| L3 | 本地可执行，仍需外部逐项核验或干预 |
| L4 | 本地可执行、验证、记录、失败停止和恢复 |
| L5 | 项目所有者可直接控制，本地系统独立闭环，外部智能体可完全离线 |

每项能力登记：能力ID、当前等级、目标等级、本地实现、外部依赖、测试证据、最后复核时间、回退方案和所有者切换决定。

## 14. 能力迁移顺序

1. 本地记录：任务、状态、内部票据、决定和证据不依赖聊天。
2. 本地知识：能够按权威资料解释项目和发现冲突。
3. 本地计划：形成任务合同、风险和验收，但不自动执行。
4. 本地只读检查：搜索、静态检查、数据核验和状态监控。
5. 本地软件执行：有界文件修改、编译、测试、差异和回退。
6. 本地训练运营：数据选择、训练编排、Token、资源和Checkpoint。
7. 本地验证审核：未见数据验证、机器审核、失败学习和修复合同。
8. 本地推理生成：影子推理通过后逐项接管正式生成。
9. 本地Runtime接口：只在独立机器发布门通过后向游戏Runtime提供合格输入。
10. Codex退出执行链：成熟能力只由本地系统执行，Codex仅只读核验。

上述顺序允许不同能力并行处于不同等级，但不得跳过某项能力自身的迁移门禁。

## 15. 每项能力的迁移条件

能力切换到本地正式执行前，必须同时满足：

1. 输入、输出、状态和失败合同明确。
2. 本地实现能够独立启动、暂停、安全停止和恢复。
3. 权限、秘密、文件范围和破坏性操作受到程序约束。
4. 正式路径不依赖聊天历史或Codex在线。
5. 全过程自动记录且具有幂等身份。
6. 失败自动阻断并保留证据。
7. 正向测试、反向门禁测试和历史回归通过。
8. 结果可以与现有通道做影子对比。
9. 性能、资源和成本达到预算。
10. 存在回退版本和恢复演练。
11. 来源、许可、依赖和原创性声明准确。
12. 机器迁移验收报告证明该能力达到目标等级并原子登记切换；Owner控制台可观察、暂停或紧急回退。

未满足条件的能力只能处于实验、辅助或影子状态。

## 16. 本地AI治理、安全与自主运行原则

1. 本地程序和不可变证据是正式系统记录；模型回答不是。
2. 生效业务与安全合同定义本地系统边界；Owner可以改变业务目标、暂停或紧急覆盖，但不是日常审批员。
3. 新模型、数据、审核实现、训练计划和能力版本发布进入本地版本化变更控制；训练、验证、审核、RuntimeFrame、记录和世界运行均不逐任务请求人工授权。
4. 文件修改、命令执行、网络访问、外部发布和破坏性操作分别设门禁。
5. 秘密不得进入提示、日志、训练数据或公开证据。
6. 正式记录不得静默覆盖，失败内容不得删除或混入正向容量。
7. 数据、代码、模型、依赖和外部服务都必须可追踪许可与版本。
8. 自动化必须具备超时、任务锁、失败停止、幂等和恢复点。
9. 任何性能提升不得通过降低业务审核门槛获得。
10. MVP条件不得固化成永久架构。
11. 对Codex的退出按能力验收，不以日期或口头判断替代证据。
12. 本文只治理本地AI能力建设，不替代项目整体治理。

## 18. 最终验收目标

整体目标完成时，应能证明：

- 项目所有者能在本地后台发起并管理全部正式任务。
- 本地系统能依据权威资料理解需求、规划任务并解释限制。
- 本地系统能安全执行软件修改、编译、测试、模型训练、验证和生成。
- 每项动作都有任务合同、内部票据、环境、日志、Token、资源、资产、结果和失败证据。
- 本地系统能自动隔离失败、提出有界修复并完成回归。
- 本地系统能管理数据、代码、模型、Checkpoint和Runtime接口版本。
- 能力逐项达到L4/L5并由机器迁移验收原子登记切换。
- 关闭Codex不会中断任何已迁移的正式业务。
- Codex只作为可选的只读监控、证据核验和技术建议来源。

## 19. 架构结论

本框架以AI Painter为首个落地模块，但目标是逐步建设覆盖整个项目工作流程的本地自研AI系统。泰国数据只承担MVP启动任务；未来能力、数据和运行范围必须可以扩展。

能力迁移必须逐项、可验证、可回退。项目所有者控制业务目标与紧急边界；本地模型负责智能能力，本地程序负责确定性执行、版本发布和证据，游戏Runtime负责世界运行，Codex随本地能力成熟逐步退出操作与执行链。
