破坏性变更规则：文档权威顺序、能力发布边界、历史证据保留规则或唯一计划表职责发生变化时必须提升版本并通过仓库级文档—合同一致性检查。

Codex等外部执行智能体不得超出当前用户任务范围；本地程序在生效业务、安全和机器合同内自主运行，不从聊天或本句推导逐步Owner审批。

## 1. 文档分类

| 分类 | 内容 | 禁止内容 |
|---|---|---|
| 项目导航 | README中的业务规格入口、正式文档入口和主要目录 | 业务定义正文、当前阻断、运行结果、下一步 |
| 智能体规则 | AGENTS中的读取、授权、安全和实施规则 | 执行历史、授权账本、训练流水 |
| 正式文档 | 业务、架构、规格、数据合同、页面合同和验收标准 | 某次运行状态、临时下一步、历史事件堆叠 |
| 唯一模块计划表 | 当前模块、目标、边界、阻断、完成条件和下一模块 | 每次命令、每个Epoch或逐次授权历史 |
| 机器证据 | `data/`、`.runtime/`和SQLite中的运行事实 | 以聊天或Markdown代替机器记录 |

## 2. 唯一计划表

全项目只允许`docs/game-world-generation/CURRENT_EXECUTION_GUIDE_20260710.md`承担计划表职责。计划表仅在模块建立、完成、失败关闭或范围实质变化时更新一次，不因每次实现、训练、测试或对话更新。

除唯一计划表外，任何Markdown不得声明临时行动指令或把临时运行状态写成正式规则。

## 3. 正式文档要求

所有项目Markdown必须包含：

- `更新时间：YYYY-MM-DD HH:mm:ss +08:00`
- 单独一行的`状态：...`
- `Codex等外部执行智能体不得超出当前用户任务范围；本地程序在生效业务、安全和机器合同内自主运行，不从聊天或本句推导逐步Owner审批。`

该句约束Codex、外部智能体和文档编辑者不得越过当前任务范围；它不构成本地自研AI运行状态机的逐步骤Owner审批门。正式文档必须明确区分“外部执行任务范围”和“本地系统在长期合同内的自主运行边界”。

正式文档必须长期有效、职责单一、引用可达。新增文件前先检查是否能合并进现有权威文件；禁止建立`history/`、`old-docs/`、`archive-docs/`或平行阶段文档树。

## 4. 运行证据

训练、验证、审核、失败、内部任务票据、外部任务范围记录、Token、Checkpoint、硬件和程序事件必须由本地程序写入不可变记录，并由SQLite建立查询索引。Markdown不得复制这些事件。

旧运行事实需要保留时保留机器证据，不在正式文档中增加“历史失效”段落。`latest.json`只作指针，不得覆盖不可变记录。

文档治理检查覆盖根目录导航与规则、`docs/` 下全部正式 Markdown，以及 `data/`、`src/` 下供人阅读的目录 README。`data/` 内数据包快照、审核快照和运行证据不属于正式文档，检查器不得要求改写或清洗这些不可变历史文件。

## 5. 修改流程

1. 确认文件职责和现有锁定规格。
2. 检查工作区已有改动和引用关系。
3. Codex等外部执行者在Owner当前任务范围内修改；本地自研AI只在生效项目合同与安全边界内自主修改。
4. 运行编码、链接、语义一致性、类型、构建及相关测试。
5. 只有模块状态发生实质变化时更新唯一计划表。

## 6. 页面与程序合同

页面结构、写入边界、训练路线、数据资格和审核门槛必须先由对应正式规格定义。控制台只读取机器证据。本地自研AI在生效合同内可以自主形成能力变更、训练、验证、发布与回退，但必须通过版本化测试、资源、安全、来源、审核和原子记录门禁；内部票据只承担幂等与证据职责。Codex等外部执行者的写操作仍受Owner当前任务范围约束。任何路径都不能依靠页面身份、开发环境、调用方布尔字段或请求者自称Owner绕过正式合同。

## 7. 文档与机器合同验收

本地正式文档整编入口为`npm run check:ai-painter-document-contracts`。它必须在不读取`.runtime`、Checkpoint或GPU状态的环境中验证：文档元数据、链接与唯一性；当前自主能力语义；历史合同原始字节和替代索引；旧Owner授权术语不得重新成为当前权威；编码与跨平台换行规则。该本地入口是当前工作区文档基线的正式验收入口；它只证明正式文档已经一致，不证明自主能力机器合同和程序已全量接入。GitHub工作流`.github/workflows/ai-painter-document-contracts.yml`如被运行，只是对同一检查的远程镜像；未运行远程CI不阻断本地文档基线结论，也不能被用来声明模型或能力通过。

本地硬件与数据行为检查和仓库级检查分离：完整23通道条件包、nearest/bilinear实际缩放行为及本地数据身份由`npm run check:ai-painter-contract-semantic-alignment`验证。仓库CI通过只能证明跟踪文件之间一致，不能冒充本地数据、GPU、训练或正式能力发布已经通过。

### 7.1 文档基线语义检查

文档检查不得只判断固定句子是否存在。至少必须结构性验证：

- 权威索引只有一个`GOV-OWNER-001`定义，业务、架构、AI Painter主体、审核存储和本地AI能力文档只引用该定义。
- 权威文档的能力、单次执行和机器审核状态枚举与总体架构逐字符合，映射关系完整。
- 现行合同、历史合同、替代索引和当前入口登记四者的路径、SHA-256和可执行性一致；历史合同必须保留，但不得被当前解析器调用。
- AI Painter四个责任阶段与Stage 0/1/2训练分辨率阶段有明确区分，当前12通道潜变量不得出现于长期不可变业务合同。
- 37条稳定需求在定义区和追踪表中各出现一次，状态只能使用正式枚举，文档工作不得把任何项提升为`machine_conformant`。
- 文档元数据的“正式目标标准”与“程序尚未全量符合”必须同时可表达，不得以文档生效掩盖实现缺口。
- 唯一当前执行登记的四个身份分离、无历史回退和`unknown_or_stale`失败闭合规则在权威索引、总体架构、审核存储和控制台规格中一致。

`active_normative_target`表示正式目标标准已生效；`program_adoption_pending`表示程序尚不能宣告对整份标准全量符合。两者同时存在是正常迁移状态，不得互相替代。
